# 词力战士（Word Warrior）M1 核心玩法需求规格说明书

> 文档状态：M1 需求规格（v1.0）
> 适用阶段：M1（MVP 核心）
> 需求句式：EARS（Easy Approach to Requirements Syntax）
> 关联文档：`README.md`、`docs/词库格式规范.md`、HTML 试玩原型 `../prototype/index.html`

---

## 一、项目概述

### 1.1 背景

「词力战士」是一款「打怪学字词」的轻竞技教育射击游戏微信小程序。玩家扮演竖屏炮台，发射字母/汉字子弹，补全上方怪兽身上的挖空单词、词语或成语；选对补全即打爆怪兽，选错扣命。游戏覆盖幼儿园到大学的多学段字词学习，一题一次机会、3 命制、每 10 题一关、按正确率出 1~3 星解锁后续关卡。HTML 试玩原型玩法已通过验证，本规格面向将其平移为正式小程序工程的 M1 阶段。

### 1.2 目标

M1 交付一个「可编译、可运行、可试玩」的核心版本，具体达成：

1. 建立小程序前端（miniprogram/）与云托管后端（server/）的工程骨架，可编译可运行。
2. 将已验证的核心战斗玩法平移为微信原生小程序（Canvas 2D 渲染游戏核心），玩法行为与原 HTML 原型保持一致。
3. 提供幼儿园→大学多学段、多题型的内置分级词库，本地 JSON 存储。
4. 支持玩家设置昵称（微信头像昵称授权容错 + 自定义输入兜底），本地存储。
5. 实现纯文本词库导入的解析与校验逻辑（最小可用，按 `docs/词库格式规范.md` 校验规则）。
6. 建立 Express + MySQL + Sequelize 后端骨架，提供用户/昵称/分数基础接口桩。

### 1.3 非目标 / 范围边界（Out of Scope）

M1 明确**不包含**以下内容（在第八节「上下文」中简列，不在 M1 需求范围内）：

- 形象 / 段位 / 皮肤系统（M2）
- 排行榜完整版（M2）
- 自定义关卡的上传、分享、审核流转（M3）
- 错题本与艾宾浩斯复习（M3）
- 每日挑战、连续签到、成就勋章、音效/BGM、学习报告（M4）
- 合规（青少年模式、防沉迷、隐私协议）完整实现（M4，仅预留接口约束）

## 二、角色与使用场景

### 2.1 核心角色

| 角色 | 说明 |
|---|---|
| 玩家 | 唯一的人类使用者。选择关卡、答题、查看结算、设置昵称、导入词库。 |

### 2.2 使用场景

- **场景 A：核心游戏**：玩家进入首页 → 选择难度/关卡 → 答题闯关 → 查看星级结算。
- **场景 B：昵称设置**：玩家首次进入（或主动）设置昵称，用于后续排行榜展示（排行榜本体属 M2）。
- **场景 C：词库导入**：玩家粘贴/导入纯文本词库，系统解析并校验，反馈行级错误。

## 三、功能需求

> 编号规则：`REQ-模块代码-序号`，模块代码：ENG=工程、GAME=战斗、DICT=内置词库、NICK=昵称、IMP=词库导入、API=后端。

### 3.1 工程初始化（ENG）

**REQ-ENG-1 前端工程骨架**
当开发者在微信开发者工具中导入 `miniprogram/` 目录时，系统 **必须** 提供可编译运行的工程骨架，包含 `app.js / app.json / app.wxss` 以及首页（index）、关卡选择（level）、游戏（game）、结算（result）、昵称（nickname）五个页面。
- 验收条件：`miniprogram/` 目录导入微信开发者工具后无编译错误，可预览运行进入首页。

**REQ-ENG-2 后端工程骨架**
当开发者在 `server/` 目录执行 `npm install && npm start` 时，系统 **必须** 提供可运行的后端服务骨架（Express + Sequelize + MySQL），包含 `index.js`、数据库连接模块、路由目录、`package.json` 与 `Dockerfile`。
- 验收条件：`server/` 依赖安装成功，`npm start` 可启动并监听端口，健康检查接口返回正常。

**REQ-ENG-3 目录结构规范**
系统 **应当** 遵循既定目录结构：`miniprogram/game/`（Canvas 游戏核心）、`miniprogram/data/`（内置词库 JSON）、`miniprogram/utils/`（词库解析/校验、配置、本地存储）、`server/routes/`（接口路由）。
- 验收条件：上述目录在工程初始化后均存在，职责划分与 README 规划一致。

### 3.2 核心战斗平移（GAME）

#### 3.2.1 页面 / 状态

**REQ-GAME-1 四屏结构**
系统 **必须** 提供四个互斥的页面（屏幕）：首页、关卡选择、游戏、结算；玩家可在首页→关卡选择→游戏→结算之间按规则流转，并可返回首页/重玩。
- 验收条件：从首页点击「开始游戏」进入关卡选择；选中关卡后进入游戏；答题结束进入结算；结算页可「再玩一次」「回首页」。

**REQ-GAME-2 竖屏炮台与画布**
当玩家处于游戏页时，系统 **必须** 使用 Canvas 2D 渲染游戏画面，呈现上方怪兽（身上带挖空题目）、下方炮台，保持竖屏布局。
- 验收条件：游戏页竖屏显示，炮台位于下方，怪兽位于上方，渲染帧率满足 3.4 节性能要求。

#### 3.2.2 出题规则

**REQ-GAME-3 每关题数与命数**
当玩家开始一关时，系统 **必须** 初始化该关为 10 题、3 条命（初始生命值 = 3）。
- 验收条件：开始关卡后题目计数显示「第 1/10 题」；生命显示 3 颗心。

**REQ-GAME-4 挖空规则**
当系统生成题目时，系统 **必须** 按题型确定挖空位置：英语单词优先挖元音字母（a/e/i/o/u）；成语挖中间某个字（避开首字）；单字/词语随机挖一字。若无对应规则则随机挖一格。
- 验收条件：对同一单词多次出题，挖空位置落在元音上（存在元音时）；成语挖空不落在首字。

**REQ-GAME-5 选项生成**
当系统出题时，系统 **必须** 生成 4 个选项（1 个正确答案 + 3 个干扰项），选项互不重复、不含与正确答案相同的字符；干扰项应优先采用「教学意义」干扰（形近/易混字符），不足时自动补齐。
- 验收条件：每题的选项数为 4，且选项间两两不同，正确答案恰好出现一次。

#### 3.2.3 答题与反馈

**REQ-GAME-6 一题一次机会（答对）**
当玩家在「待答题（idle）」状态选中正确字符时，系统 **必须** 发射炮弹击中挖空处、填充正确字符，并给出正向反馈：得分 +100、连击 +1、绿色 ✓ 反馈、爆炸粒子、怪兽头顶冒星星、补全释义提示；随后进入下一题。
- 验收条件：选中正确项后得分增加 100，挖空格填充正确答案，展示 ✓ 反馈，约 0.7 秒后进入下一题。

**REQ-GAME-7 一题一次机会（答错）**
当玩家选中错误字符时，系统 **必须** 判定为答错，本选项作废，触发「怪兽逼近 + 抖动 + 红色闪光」动画，并在约 0.6 秒后扣 1 命、连击归零，再进入下一题；且本题不再允许二次作答。
- 验收条件：选错后当前题不可再次作答，生命减 1，连击清零，正确字符以错误色填充并提示正确答案。

**REQ-GAME-8 怪兽自然下沉判负**
当玩家处于未作答状态且迟迟不答时，系统 **必须** 让怪兽以固定速度自然下沉；若怪兽下沉至危险线（dangerY），则系统 **必须** 按「答错」处理（判负并扣命）。
- 验收条件：怪兽未作答时持续下沉，下沉到危险线后触发与答错一致的扣命流程。

**REQ-GAME-9 连击提示**
当玩家连续答对达到 2、3、5 题时，系统 **必须** 在画面中央弹出对应连击提示（2 连击 / 3 连击 / 5 连击及以上为庆祝文案）。
- 验收条件：连续答对第 2、3、5 题时分别出现连击提示。

**REQ-GAME-10 空格呼吸反馈**
当玩家处于待答题状态时，系统 **必须** 让挖空格以「闪烁 + 呼吸缩放」动画呈现，提示待填状态；已填充后停止呼吸动画并显示填充字符。
- 验收条件：待答时空格可见闪烁/缩放动画，填充后动画停止、显示填充字符。

#### 3.2.4 结算与星级解锁

**REQ-GAME-11 整局失败**
当玩家生命归零（3 命耗尽）时，系统 **必须** 立即结束本局并进入结算页，标题展示失败态（如「再接再厉！」），不写入星级。
- 验收条件：3 命耗尽直接进入结算页，不计星、不新增星级存档。

**REQ-GAME-12 星级评定**
当玩家答完 10 题时，系统 **必须** 按正确率给出星级：正确率 ≥ 90% 得 3 星，≥ 70% 得 2 星，≥ 40% 得 1 星，< 40% 得 0 星。
- 验收条件：正确率 90%/70%/40% 三个阈值边界分别对应 3/2/1 星，40% 以下为 0 星。

**REQ-GAME-13 通关写星与取最优**
当玩家通关（答完 10 题）时，系统 **必须** 将本次星级按「年级+关卡」写入本地存档；若历史已存在更高星级，则保留最高值。
- 验收条件：重复通关同一关，星级存档取历史最大值。

**REQ-GAME-14 关卡解锁规则**
系统 **必须** 默认解锁每个难度的第 1 关；第 N 关（N>1）须在前一关（N-1）达到 ≥1 星时解锁。
- 验收条件：第 1 关直接可选；未满 1 星时后续关卡锁定（点击抖动提示、不可进入）。

**REQ-GAME-15 结算数据展示**
当玩家进入结算页时，系统 **必须** 展示：星级（★/☆）、得分、答对题数（x/10）、正确率百分比，并提供「再玩一次」「回首页」操作。
- 验收条件：结算页各项数值与本局实际结果一致。

### 3.3 内置分级词库（DICT）

**REQ-DICT-1 学段覆盖**
系统 **必须** 内置覆盖「幼儿园、小学 1-2、小学 3-4、小学 5-6、初中、高中、大学」共 7 个学段的分级词库，每个学段至少覆盖一种题型。
- 验收条件：可在游戏中按学段选择词库，各学段均有可出题的词条。

**REQ-DICT-2 题型覆盖**
系统 **必须** 内置支持 `docs/词库格式规范.md` 定义的 8 种题型（w1 单词挖 1 格、w2 单词挖多格、c1 汉字/成语挖 1 字、c2 词语/成语挖多字、xhy 歇后语、zc 组词、fill 英语句子填空、trans 中英互译），内置词库按此类型码组织。
- 验收条件：8 种类型码均可被解析，且内置数据中存在对应示例词条。

**REQ-DICT-3 词条结构**
系统 **必须** 保证每条内置词条包含：题目、答案、提示/释义，并可选择性包含干扰项；挖空位置用 `*` 显式标注，未标注时由系统默认挖空（单词优先挖元音、成语挖中间字）。
- 验收条件：无 `*` 标注的词条仍可正常出题并生成挖空位置。

**REQ-DICT-4 本地 JSON 存储**
系统 **必须** 以内置 JSON 文件形式存储分级词库，随小程序包分发，不依赖网络即可加载出题。
- 验收条件：断网状态下仍能加载内置词库并开始游戏。

**REQ-DICT-5 题库可扩展性**
系统 **应当** 保持词库数据与出题逻辑解耦，使后续新增学段/题型词条无需改动出题逻辑。
- 验收条件：仅通过新增/修改词库 JSON 即可扩展题库，无需改动答题核心代码。

### 3.4 昵称功能（NICK）

**REQ-NICK-1 微信头像昵称授权容错**
当玩家首次设定昵称并授权使用微信头像昵称时，系统 **必须** 正常获取并填充微信昵称；若玩家拒绝授权，系统 **必须** 提供手动输入的自定义昵称兜底，不阻塞游戏进入。
- 验收条件：拒绝授权后仍可通过自定义输入完成昵称设置并继续进入游戏。

**REQ-NICK-2 昵称本地存储**
当玩家设置昵称后，系统 **必须** 将昵称持久化到本地存储；再次进入时默认读取已存昵称。
- 验收条件：设置昵称后退出并重进，昵称仍被保留并展示。

**REQ-NICK-3 昵称输入约束**
当玩家自定义输入昵称时，系统 **必须** 校验昵称长度与内容：默认长度不超过 12 个字符（或可配置）、去除首尾空白、不允许为空；不合规时给出提示且不保存。
- 验收条件：空昵称、超长昵称均被拦截并提示，合规昵称正常保存。

**REQ-NICK-4 昵称入口与提示**
系统 **必须** 在首页提供昵称设置入口，并在玩家未设置昵称时以占位（如「未设置昵称」）提示引导补全。
- 验收条件：首页可见昵称入口，未设置时显示占位引导，可点击进入设置。

### 3.5 词库导入解析/校验（IMP）

**REQ-IMP-1 纯文本解析**
当玩家粘贴或导入纯文本词库时，系统 **必须** 按「类型码|题目|答案|提示/释义|干扰项(可选)」的行格式解析，一行一条，字段以 ASCII `|` 分隔，并自动纠正全角 `｜` 为半角。
- 验收条件：合法多行文本可被正确解析为词条列表；全角分隔符被自动纠正。

**REQ-IMP-2 类型码校验**
当解析到某行时，系统 **必须** 校验其类型码属于 8 种合法类型码之一，否则报错并定位到行号。
- 验收条件：非法类型码行被拒绝并提示「第 N 行：类型码…不认识」。

**REQ-IMP-3 字段数校验**
系统 **必须** 校验每行字段数至少为 3（题目、答案、提示/释义），缺「提示/释义」时报错定位到行号；缺「干扰项」可接受。
- 验收条件：字段不足的行被拒绝并提示定位行号；缺干扰项的行正常通过。

**REQ-IMP-4 挖空一致性校验**
当题型为 w2/c2 时，系统 **必须** 校验题目中 `*` 的数量与答案长度一致，否则报错。
- 验收条件：`*` 数量与答案长度不符的行被拒绝并提示「挖空数(*)与答案不符」。

**REQ-IMP-5 答案一致性校验**
系统 **必须** 校验答案字符均属于题目字符集（去除 `*` 后），否则报错。
- 验收条件：答案含题目外字符的行被拒绝并提示「答案不在题目中」。

**REQ-IMP-6 干扰项校验**
当存在干扰项时，系统 **必须** 校验干扰项不含正确答案，否则报错。
- 验收条件：干扰项与正确答案重复的行被拒绝并提示。

**REQ-IMP-7 重复词条校验**
系统 **必须** 检测相同「题目」的重复词条，并提示重复及其首次出现行号。
- 验收条件：重复题目被识别并提示「第 N 行：与第 M 行题目重复」。

**REQ-IMP-8 敏感词校验**
系统 **必须** 对导入内容进行敏感词过滤，命中过滤词库的行被拒绝。
- 验收条件：含敏感词的行被拒绝并提示「包含敏感内容」。

**REQ-IMP-9 行级错误反馈**
当校验失败时，系统 **必须** 汇总全部错误并以「行号 + 原因」形式反馈给玩家，而非仅返回首个错误。
- 验收条件：多行有错时一次性展示所有错误及对应行号与原因。

**REQ-IMP-10 自动生成缺省干扰项**
当词条未提供干扰项时，系统 **必须** 按题型算法自动生成干扰项，保证本题可正常出题。
- 验收条件：缺干扰项的词条导入后可正常进入战斗并生成 4 个选项。

### 3.6 后端骨架（API）

**REQ-API-1 服务初始化**
当后端服务启动时，系统 **必须** 建立 Express 应用、完成 MySQL 连接初始化（Sequelize），对外监听配置端口。
- 验收条件：服务启动成功，MySQL 连接失败时报错并终止启动（或明确日志）。

**REQ-API-2 用户接口桩**
系统 **必须** 提供基础用户接口桩：获取/创建用户（含微信 OpenID 识别），返回统一响应结构 `{ code, data }`。
- 验收条件：调用用户接口可返回 `code=0` 及结构一致的数据。

**REQ-API-3 昵称接口桩**
系统 **必须** 提供昵称读写接口桩：设置昵称、读取昵称，输入含非法内容时返回明确的业务错误码。
- 验收条件：读写昵称返回结构一致，非法昵称返回非 0 错误码。

**REQ-API-4 分数接口桩**
系统 **必须** 提供分数相关接口桩：上报本局得分/星级、查询用户历史最佳成绩。
- 验收条件：上报与查询返回结构一致，可往返存取。

**REQ-API-5 微信 OpenID 透传**
系统 **必须** 支持通过 `x-wx-source` / `x-wx-openid` 请求头识别小程序用户 OpenID（沿用云托管约定）。
- 验收条件：携带微信来源头时，接口能取到并返回对应 OpenID。

## 四、非功能需求

**REQ-NFR-1 渲染性能**
当玩家进行游戏时，系统 **必须** 保证 Canvas 游戏核心以目标 60 FPS 渲染，单帧耗时不超过约 16ms，不出现可感知卡顿。
- 验收条件：主流机型试玩 10 题无卡顿，帧率稳定接近 60。

**REQ-NFR-2 离线可用（核心玩法）**
当玩家无网络时，系统 **必须** 保证内置词库加载、关卡选择、游戏、结算、昵称等核心流程可用；仅需联网的接口（如分数上报）在无网时降级为本地暂存或静默失败，不阻塞游戏。
- 验收条件：断网时核心玩法完整可玩，联网功能不导致崩溃。

**REQ-NFR-3 兼容性**
系统 **必须** 兼容微信小程序基础库及主流移动设备（iOS/Android 竖屏），Canvas 2D 接口在目标基础库版本可用。
- 验收条件：iOS 与 Android 真机竖屏试玩正常。

**REQ-NFR-4 数据安全与合规预留**
系统 **必须** 在涉及玩家昵称等个人信息时遵循「最小必要」原则，仅在必要场景读取，并预留隐私政策/用户协议入口（完整合规属 M4）。
- 验收条件：功能层面不强制获取无关授权，拒绝授权不阻塞核心玩法。

**REQ-NFR-5 参数可配置**
系统 **应当** 将魔法数字（怪兽下沉速度、答错逼近距离/时长、每关题数、初始命数、星级阈值等）集中为可配置项，便于调难度。
- 验收条件：修改配置即可调整玩法强度，无需改动核心逻辑。

**REQ-NFR-6 可维护性**
系统 **应当** 具备清晰的模块划分（金管页面/WXML 页面与 Canvas 游戏核心分离、词库解析与存储分离），关键复杂逻辑附注释。
- 验收条件：代码组织与 README 目录规划一致，核心算法有注释说明。

## 五、数据需求

### 5.1 词条（领域对象）

1. **类型码**：必须为 8 种合法值之一（w1/w2/c1/c2/xhy/zc/fill/trans）。
2. **题目**：非空字符串；挖空位置可用 `*` 标注；`*` 数量与答案长度的约束随题型而定。
3. **答案**：非空；字符必须属于题目字符集。
4. **提示/释义**：非空；英语题填中文释义，汉字/成语题填释义或拼音。
5. **干扰项**：可选；以 `,` 分隔；不得包含正确答案。
6. **学段**：属于 7 个学段之一（用于内置词库分级）。
7. **题库唯一性**：同一学段内「题目」应唯一（重复需去重或提示）。

### 5.2 玩家本地数据

1. **昵称**：非空字符串，长度不超过 12 字符，去除首尾空白。
2. **星级存档**：按「难度 + 关卡」维度记录星级（0~3），取历史最高值。
3. **关卡解锁状态**：由星级存档推导（第 1 关默认解锁，后续关需前一关 ≥1 星）。
4. **本地游戏进度/状态**：单局得分、答对题数、当前题号、生命值（内存态，不要求持久化）。

### 5.3 后端用户/成绩数据（接口桩约定）

1. **用户标识**：以微信 OpenID 为唯一标识。
2. **昵称**：存储于用户维度的可读写字段。
3. **成绩记录**：包含得分、正确题数、正确率、星级、关卡等可上报字段；支持查询历史最佳。

> 说明：本节描述领域对象的逻辑约束，不规定具体表结构、字段类型或存储索引（属设计阶段范畴）。

## 六、接口需求（后端接口桩契约）

> 统一响应结构：`{ code: number, data?: any }`，`code=0` 表示成功，非 0 表示业务错误。

| 接口 | 方法 | 语义 | 关键入参 | 关键出参 |
|---|---|---|---|---|
| 获取/创建用户 | POST | 识别并返回用户，无则创建 | OpenID（请求头透传） | 用户标识 |
| 读取昵称 | GET | 返回当前用户昵称 | 用户标识 | 昵称 |
| 设置昵称 | POST | 写入昵称，校验合法性 | 用户标识、昵称 | 写入结果 |
| 上报成绩 | POST | 记录一局成绩 | 用户标识、得分、正确数、星级、关卡 | 上报结果 |
| 查询最佳成绩 | GET | 返回用户历史最佳 | 用户标识 | 最佳成绩 |

验收条件：上述接口均返回 `{ code, data }` 结构；非法入参返回非 0 业务码；接口仅为 M1 可用的桩（后续 M2 排行榜等基于此扩展）。

## 七、验收标准汇总（M1 完成标准）

M1 达到「可编译、可运行、可试玩」，逐项满足：

1. **工程**：前端 `miniprogram/` 与后端 `server/` 骨架齐备，前端可预览、后端可启动。
2. **战斗**：四屏流转完整，竖屏炮台 + Canvas 射击玩法、挖空补全、一题一次机会、3 命制、10 题一关、星级解锁（≥90/70/40%）、连击/答错逼近/✓ 反馈/空格呼吸均与原型一致（REQ-GAME-1~15）。
3. **词库**：内置 7 学段、8 题型 JSON 词库，本地加载可离线出题（REQ-DICT-1~5）。
4. **昵称**：微信授权容错 + 自定义输入兜底 + 本地存储（REQ-NICK-1~4）。
5. **导入校验**：纯文本解析 + 7 项校验规则 + 行级错误反馈 + 缺省干扰项自动生成（REQ-IMP-1~10）。
6. **后端**：Express + MySQL + Sequelize 骨架，用户/昵称/分数接口桩可用（REQ-API-1~5）。
7. **非功能**：60 FPS、离线核心可用、真机兼容、参数可配置、合规预留（REQ-NFR-1~6）。
