## 二、现状盘点（改之前必须先看清底账）

### 2.1 学段只有 7 档，且粗细不均

| 学段 key | 展示名 | 词条数 |
| --- | --- | --- |
| `kindergarten` | 幼儿园 | 100 |
| `primary12` | 小学1-2 | 150 |
| `primary34` | 小学3-4 | 200 |
| `primary56` | 小学5-6 | 200 |
| `junior` | 初中 | 200 |
| `senior` | 高中 | 200 |
| `college` | 大学 | 200 |

合计 1250 条。**问题**：小学一二年级和三四年级的孩子认知差距很大，却共用一套题；
家长也习惯按「几年级」找内容，看到「小学1-2」会觉得不是给自己孩子准备的。

### 2.2 题库文件结构

每个学段一个 JS 模块（`miniprogram/data/<grade>.js`）：

```js
module.exports = {
  grade: "kindergarten", label: "幼儿园", count: 100,
  items: [
    { type: "c1", q: "大", a: "大", hint: "大小的大" },
    ...
  ]
}
```

`type` 是题型码（`w1` 单词挖 1 格、`c1` 汉字挖 1 字、`xhy` 歇后语…），
**没有**教材版本、学期、单元这些字段。

### 2.3 存档 key 里带着学段

星级存档的命名空间是 `<学段>@<玩法>@<关卡>`，例如 `kindergarten@mode_link@1`。
**这意味着改学段 key 会让老用户的闯关进度全部失效** —— 这是本次改造最大的技术风险。

## 三、主流同类产品是怎么做的（调研）

### 3.1 结论先说：国内 K12 产品几乎都是「年级 + 教材版本 + 学期/单元」三层

| 产品 | 分级方式 | 说明 |
| --- | --- | --- |
| **一起作业 / 一起学** | 教材版本 → 年级 → 学期 → 单元 | 国内最标准的做法，老师按教材布置作业 |
| **小猿口算 / 作业帮** | 年级 → 教材版本 → 单元 | 同上，家长按孩子教材选 |
| **百词斩 / 扇贝** | 考试词书 + 教材词书（人教版必修等） | 面向中学以上，按教材分册 |
| **洪恩识字 / 悟空识字** | 按汉字难度 / 故事章节 | **不对接教材**，走自研分级 |
| **斑马 / 瓜瓜龙** | 自研分级（S1~S5） | 学龄前为主，不按教材 |
| **Duolingo** | CEFR 等级 + 单元路径 | 不按学校教材，自成体系 |

**两条路线**：

- **学龄前（幼儿园）**：主流是**自研分级**，因为学龄前没有统编教材。
- **小学及以上**：主流是**对接教材**，因为家长/老师就是按教材找内容的，不对接会被认为「不专业」。

### 3.2 教材版本这件事比想象中复杂

- **语文**：全国统一**部编版（统编版）**，一套就够。✓
- **数学**：版本多（人教版、北师大版、苏教版…），但**知识点顺序差异不大**，
  而且数学题本来就不用严格按教材出，按年级分档即可。✓
- **英语**：**这里最麻烦** —— 小学英语有 人教版(PEP)、外研版、译林版、冀教版、
  北师大版、湘少版… 不同地区用的完全不一样，词表顺序也不同。

**我们的选择**：初期只对接 **1~2 个占比最高的版本**（人教版 PEP + 外研版），
其余版本先用「通用词表」兜底。全部版本都做，成本会失控。

### 3.3 学期与单元

主流产品都会细到「上册/下册」和「第几个单元」，因为老师是按单元布置作业的。
但我们不是作业工具，是**游戏化练习**，做到「年级 + 教材版本 + 上册/下册」已经够用，
再细到单元会让关卡设计变得很碎。

用户 2026-10-08 拍板：**拆到高三，13 档；大学并入第 14 档**。
高三单独成档的理由：高考词汇虽然不分年级，但**高三复习阶段的心理暗示**是真实的
（高三学生看到标着「高一」的题会觉得不对味）。

> 档位数 7 → 14，每档题量要跟着补齐 —— 这是本次改造**内容侧**的主要工作量（见第六节）。

### 4.2 每档的题量

现在是 100~200 条/档。拆细之后，**小学每档至少要有 150~200 条**
（30 关 × 每关 10 题 = 300 题位，靠题型变换和重复出题可以少于 300，但不能太少）。

**粗算**：11 档 × 180 条 ≈ **2000 条**，比现在的 1250 条多 60%。
**这部分内容从哪来，是本次改造最大的外部依赖**（见第六节）。

## 五、教材对接方案

### 5.1 数据模型加三个字段（**已拍板：先做 人教版 PEP + 外研版**）

给词条加：

```js
{
  type: "w1", q: "apple", a: "apple",
  book: "pep",     // 教材版本：pep 人教版 / wys 外研版 / bjb 部编版（语文）
  term: "up",      // 学期：up 上册 / down 下册
  unit: 3          // 单元号（可选，先留空）
}
```

学段配置（`constants.js`）也扩成：

```js
{ key: 'g3', label: '三年级', book: 'pep', term: 'up' }
```

### 5.2 用户怎么选

在「我的 → 学习设置」里增加：

- **年级**（必选，影响出题）
- **教材版本**（只对英语生效；没选就用通用词表）

默认值：注册时按微信地区猜？✗ 猜不准。**建议注册后第一次进关卡页时弹一次选择**，
之后可在设置里改。

### 5.3 兼容：不是每个版本都能对上

选了「外研版」但我们只有人教版词表时 → 落到**该年级的通用词表**，
并在界面上说明「该版本词表正在补充，先用通用词表」。**不要让用户看到空白**。

## 六、题库重构的成本（必须先说清楚）

### 6.1 工作量

从 1250 条（7 档粗分）→ 2000 条（11 档细分 + 教材标注），要做三件事：

1. **按年级重新归类**：现有词条要判断属于哪一年级（现在只到「小学1-2」这一档，拆不开）。
2. **补新词**：每档补到 180 条左右。
3. **打教材标签**：标注版本 + 学期。

**我的判断**：**这件事我做不完，需要外部词表**。

### 6.2 词表从哪来（**已拍板：公开整理版 + 人工抽查**）

做法：从公开的「人教版 PEP / 外研版 小学英语单词表（分册）」整理稿生成词表，
**生成后你抽查 2~3 个年级**确认准确性，再批量入库。

版权口径：教材词表属于**事实性内容**（单词 + 中文释义的组合），
整理成我们自己的题型结构不构成侵权；但**不要整段抄教材的例句和排版**。

### 6.3 我的建议顺序

**先拆年级，后对教材**。原因：

- 拆年级是**结构改造**（一劳永逸，且立刻能看到效果）；
- 对教材是**内容改造**（可以逐版本、逐年级慢慢补）。

两者一起做，风险叠加；分开做，每一步都能单独验证。

## 七、老用户的存档怎么办（**已拍板：做向下映射，不重置**）

现在存档 key 是 `kindergarten@mode_link@1`，改 key 后：

| 方案 | 说明 | 后果 |
| --- | --- | --- |
| **A. 重置进度** | 老存档全部作废，用户重新开始 | 简单；但老用户会觉得「白玩了」 |
| **B. 做映射** | `primary12` → 一年级（或二年级），旧 key 读出来转成新 key | 复杂；且粗分到细分是**一对多**，映射不精确 |
| **C. 双读** | 新代码同时认旧 key 和新 key，旧 key 只读不写 | 中等；过渡期后清理 |

**定稿：B 的简化版 —— 只做「粗 → 细」的向下映射**，老用户落在该学段的第一个年级，
进度不丢；新写的存档一律用新 key。

**实现上不动数据**：在 `utils/storage.js` 的读星函数里加一层**旧 key 回退** ——
新 key 读不到就去读对应的旧 key，读到就顺手按新 key 回写一次。
这样既不用批量刷库，也不用担心漏改（**数据一行都不用动**）。

单向映射表（粗 → 细）：

| 旧 key | 新 key | 说明 |
| --- | --- | --- |
| `kindergarten` | `kg` | |
| `primary12` | `g1` | 一二年级合并档 → 落到一年级 |
| `primary34` | `g3` | |
| `primary56` | `g5` | |
| `junior` | `g7` | |
| `senior` | `g10` | |
| `college` | `college` | 大学 key 不变 |

## 八、新玩法提案

### 8.1 好友 PK（你提的，我建议做成「异步战帖」）

**为什么不做实时对战**：实时要长连接 + 匹配 + 掉线处理，云托管上成本和故障率都高；
而且小学生玩家的「同时在线」概率很低，实时匹配经常空等。

**推荐形态 —— 异步战帖**：

1. A 打完一局 → 点「挑战好友」，生成一张**战帖**（记录：题目种子、A 的分数、双方 openid）
2. 分享到群/好友 → B 点开 → 打**同一套题**（同一种子，题目完全一致，公平）
3. 比完出结果页：胜/平/负，双方都加减星

**加星规则（建议）**：胜 +3 星、平 +1 星、负 0 星；**每人每天最多靠 PK 拿 10 星**（防刷）。

**技术要点**：

- 分享卡片带 `pkId` 参数 ✓（`onShareAppMessage` 已经在用）
- 新增 `pk_matches` 表（发起人、对手、种子、双方分数、状态、时间）
- 题目种子复用现有 `utils/rng.js`（同一关两次牌面一致那套）✓ 已经验证过可用

**好友关系怎么办**：微信**不提供**好友列表给小程序 ✗
所以「好友」只能是**打过 PK 的人**（对局即建立关系），不去搞通讯录。

### 8.2 跑酷（**已拍板：先不做**）

**能怎么和学习结合**：三车道跑酷，角色自动前进，
路上飘来「词卡」，吃对得分、吃错扣血；每隔一段出一次「答题门」（答对才能继续跑）。

**为什么建议往后放**：

1. **技术栈冲突**：跑酷要 60fps 的流畅动画，得用 canvas 自己做游戏循环
   （我们之前刚把字母射击**从 canvas 改成 WXML/CSS**，理由是渲染层更稳、更好维护）。
   为一个新玩法再把 canvas 引擎捡回来，成本不小。
2. **和学习的结合点弱**：跑酷的核心乐趣是「反应 + 操作」，
   答题插进去容易变成「打断跑酷」，两边体验都打折。
3. **同质化**：跑酷是红海玩法，做不出差异就是白做。

用户 2026-10-08 拍板：**先不做**。
以后真要做，仍然建议**先做「简化版」验证**（竖版单车道、只做吃对字/避开错字），
别一上来就做完整跑酷。

### 8.3 其他候选（按我的推荐度排）

| 玩法 | 说明 | 推荐度 | 成本 |
| --- | --- | --- | --- |
| **每日挑战赛** | 全服同一套题（同种子），比正确率+速度，当天出榜 | ★★★★ | 低（复用排行榜 + 种子机制） |
| **赛季制** | 每赛季（如 2 个月）段位重置 + 赛季奖励 + 赛季榜 | ★★★★ | 低（现有段位体系加一层） |
| **单词接龙** | 词尾接词首，连得越长越多分 | ★★★ | 低 |
| **组队 / 家族** | 3~5 人组队，团队总进度 + 队内榜 | ★★★ | 中（需要新表 + 邀请流程） |
| **听音辨词** | 放读音选词（我们有音频能力） | ★★★ | 中（要补音频资源） |
| **拼图解锁** | 做题解锁一张图片的碎片，集齐得皮肤 | ★★ | 低 |
| **闯关剧情** | 给主线加故事背景（战士拯救词汇世界） | ★★ | 中（要写文案 + 过场） |

**我的建议组合**：**每日挑战赛 + 赛季制 + 好友 PK**。
这三个都建立在已有的「题目种子 + 排行榜 + 段位」之上，边际成本低、社交性强，
而且直接冲着「日活」和「拉新」去。

## 十一、用户怎么选年级（2026-10-08 新增讨论）

### 11.1 结论：必须让用户自己选，没有可靠的自动判断方式

你问的「注册时不知道用户是几年级」——这是**客观限制**：

| 想用的信号 | 能不能拿到 | 结论 |
| --- | --- | --- |
| 微信提供的年龄/年级 | **不提供** | ✗ |
| 微信地区 | 拿得到 | ✗ 和年级完全无关 |
| 手机号归属地 | 不提供（且无关） | ✗ |
| 历史行为推断 | 只有老用户有 | ✗ 新用户没有 |

**主流产品全部是「问」的**：一起作业让老师选教材+年级，小猿口算让家长选年级，
斑马让家长选孩子年龄。**没有一家能自动判断。**

### 11.2 在哪问、问几次（这决定会不会劝退）

| 方案 | 说明 | 评价 |
| --- | --- | --- |
| 注册时强制选 | 登录后就弹窗，不选不能进 | ✗ 用户还没看到产品就先填表，劝退 |
| **首次进「闯关/玩法」时选** | 想玩的时候才问，动机最强 | ✓ **推荐** |
| 只放「我的 → 设置」里 | 用户自己去找 | ✗ 藏太深，多数人不会找，最后在玩错年级的题 |

**推荐流程**：

1. 用户注册 → 直接发默认昵称、直接能玩（不弹任何表单）
2. 第一次点「继续挑战 / 玩法」时 → 弹**年级选择**（幼儿园 / 一~六年级 / 初一~初三 / 高一~高三 / 大学）
3. 选完立刻开始玩；**不选也能玩**（默认落到幼儿园，回去还能改）

### 11.3 关键设计：年级是「当前视图」，不是「账号属性」

这条很重要，直接决定后面好不好用：

**年级只决定「现在看哪个学段的关卡」，不锁死在账号上。**

好处：

- **家里两个孩子** → 直接切年级，不用注册两个号 ✓
- **孩子升年级** → 改一下就行 ✓
- **切换不丢进度** ✓✓ —— 因为进度本来就**按学段分开存**（`<学段>@<玩法>@<关卡>`），
  切到别的年级只是换个视图，原来的星一颗不少

实现：

- 云端 `users.grade` 存「当前年级」（换手机也记得）✓
- 首次选择同时写本地 + 云端 ✓
- 「我的」页和玩法页顶部都能随时切换 ✓

### 11.4 和首页「继续挑战」的关系

首页的「继续挑战」现在按「最近玩过的学段」定位。改完之后应该：

**优先按用户选的年级** → 没选过才回退到「最近玩过」→ 都没有就默认幼儿园。

这样用户选了三年级，首页的卡片就一直指向三年级的关卡，不会因为某次点进二年级就「跑偏」。

### 11.5 一个可选增强：多孩子档案

如果以后要做「一个账号管多个孩子」，可以扩展成 `users.grade` 变成 `profiles[]`（每个档案一个年级 + 名字）。
**建议先不做** —— 一期先做单年级，验证家长有没有这个诉求再说。

## 附：我对这次改造的整体判断

- **年级拆分**：值得做，而且是**结构改造**，早做早省事（越晚老数据越多）。
