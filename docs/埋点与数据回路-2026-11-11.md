# 埋点与数据回路（2026-11-11 起）

> 背景：发布之前所有迭代决策都靠内部审查和拍板，没有任何用户行为数据。用户 2026-11-11 拍板：
> **发布后第一件事是搭一个最小的数据回路**（只埋 5 个事件），先回答三件事：
> ① 新用户在第几关流失；② 21 个玩法哪个真被反复玩；③ 分享卡片被点开几次。
> 本文是这套埋点的**唯一说明文档**：事件定义、挂点、读法、隐私与已知取舍。

---

## 一、只埋 5 个事件

| 事件 | 含义 | 客户端挂点 | 关键字段 |
|---|---|---|---|
| `visit` | 进入小程序（**一天只记一次**） | `miniprogram/app.js` `onLaunch` | `scene`（启动场景值） |
| `game_start` | 开始一局 | `pkg-games/level/level.js` `_startGame()`、`pkg-games/puzzle-level/puzzle-level.js` `onLevelTap` | `game_type` / `grade` / `level` |
| `game_end` | 打完一局 | `utils/play-report.js` `reportPlay()`（21 个玩法的统一出口） | `game_type` / `grade` / `level` / `stars` / `win` |
| `share_open` | 从分享卡片进入 | `app.js` `onLaunch` / `onShow`，按启动场景 `1007 / 1008 / 1044` 自动识别 | `scene` |
| `d1_return` | 次日回访 | **服务端派生**（当天有 `visit` 且前一天也有 `visit` 时写入） | `scene`、`payload=from=derived` |

**为什么 `share_open` 用启动场景识别**：不需要给 40 多个页面的分享路径都加 `?from=share`，
微信启动参数里的 `scene` 本来就是「从哪进来的」，1007（单聊卡片）/1008（群聊卡片）/1044（带
shareTicket 的卡片）就是分享进入。零侵入、不会漏。

**为什么 `d1_return` 服务端派生**：容器没有常驻定时任务（最小实例数 ≥1 才有 cron），
在收到今天的 `visit` 时顺手查一眼昨天有没有 `visit`，是零成本且幂等的做法。

## 二、数据落库

表 `track_events`（建表脚本 `docs/sql/2026-11-11-埋点建表.sql`；生产启动由
`server/ensure-tables.js` **自动补建**，push 即部署，不需要人工执行 SQL）。

| 列 | 说明 |
|---|---|
| `openid` | 网关注入的用户标识（**业务登录态的游客也有**——埋点统计的是所有玩家） |
| `event` | 上面 5 个事件之一 |
| `day` | 北京时间自然日 `YYYY-MM-DD`（与 `checkin_records.date` 同口径，避免 UTC 在 00:00~08:00 算错天） |
| `game_type` / `grade` / `level` | 玩法 key / 学段 / 关卡号 |
| `scene` | 启动/分享场景值 |
| `stars` / `win` | 本局星级 0~3 / 是否通关 0-1 |
| `duration_ms` / `payload` | 预留（当前基本为 0 / 空） |

索引：`(day,event)` 出报表、`(openid,day)` 留存排障、`(event,game_type)` 玩法漏斗。

**写入接口**：`POST /api/track`，body `{ events: [...] }`，单批 ≤20 条。
客户端在 `miniprogram/utils/track.js`：本地队列上限 100 条、20 条一批、失败保留补发、
成功才出队；`visit` 服务端一天去重；同一天同一用户最多入库 **500 条**（防刷，超限丢弃但返回成功，
端上不会无限重试）。

---

## 三、环境闸门（很重要）

`miniprogram/utils/track.js` 只在 **release（线上）/ trial（体验版）** 上报；
**开发者工具 `develop` 一律不上报** —— 否则 E2E 每跑一次就往线上库灌一批假事件，
数据回路第一天就被污染。单测覆盖了这条规则。

本地要看上报效果：先把存储项 `ww_track_force` 置为 `'1'`，再操作页面。

---

## 四、隐私口径

- 只记**行为**：玩法 key、学段、关卡号、星级、场景值；
- **不记**内容：不碰昵称、头像、答案、词条正文、设备号；
- openid 是埋点的唯一身份维度，与业务登录态无关，不能反查手机号等任何个人信息。

## 五、怎么看数（发布后用）

### 1. 管理端汇总接口（推荐）

`GET /api/admin/track/summary?days=7`（需要管理员身份，与现有管理接口同一套鉴权）。

返回四块：

- `daily[]`：每天的 `visitUsers`（活跃）、`newUsers`（新增）、`visitCount`、`gameStart`、
  `gameEnd`、`shareOpen`、`d1Return`、`d1Rate`（当日次日回访率，%）
- `gameFunnel[]`：每个玩法的 `start` / `end` / `finishRate`（开局→完局率）
- `levelFunnel[]`：`game_end` 按关卡号的分布 —— **第 N 关完局数骤降就是流失点**
- `totals`：区间合计（含整体 `d1Rate`）

> 管理页的**可视化卡片下一版再做**（先跑一周数据、口径稳定了再固化，避免 UI 做早白做）。

### 2. 直接 SQL（临时排查）

```sql
-- 每日活跃 / 新增 / 回访
SELECT day, COUNT(DISTINCT openid) AS dau FROM track_events
WHERE event='visit' AND day >= '2026-11-12' GROUP BY day ORDER BY day;

-- 关卡流失：按关卡号看完局数（找骤降点）
SELECT level, COUNT(*) AS ends FROM track_events
WHERE event='game_end' AND day >= '2026-11-12' GROUP BY level ORDER BY level;

-- 玩法漏斗
SELECT game_type,
       SUM(event='game_start') AS starts,
       SUM(event='game_end')   AS ends
FROM track_events WHERE day >= '2026-11-12' GROUP BY game_type ORDER BY starts DESC;

-- 分享卡片被点开
SELECT day, COUNT(*) AS opens FROM track_events
WHERE event='share_open' AND day >= '2026-11-12' GROUP BY day ORDER BY day;
```

## 六、口径与取舍（改之前先看）

1. **`visit` 一天一条**：算 DAU/留存够用；不记次数（要「打开次数」得再加事件）。
2. **`game_start` 在真正跳转对局前记**：新关会先弹「认词预习」，用户点取消不算开局 ——
   这样 `start` 和 `end` 才能对上。
3. **`game_end` 以 `play-report` 为准**：只报了星级、没逐题正确的休闲玩法（数独/2048…）
   同样会记 `game_end`，`stars` 是唯一质量信号。
4. **游客也记**：新用户大概率先玩后登录，只统计登录用户会低估流失。
5. **不设自动清理**（用户拍板）：单行约 150 字节，当前量级一年几十 MB；查询一律带 `day >=`。
6. **数据是「我们觉得」的替代品，不是 KPI**：第三批例句、下个玩法选型等决策，先看这份
   曲线再拍板（内容包预警：老用户活跃下滑前就把第二个内容包备好，而不是之后）。
