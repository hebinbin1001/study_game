## 九、对齐拍板结论（2026-09-08 评审确认）

1. **资产体系**：以「星 / 段位」为长期资产；**金币不做**（教育合规、避免站内经济复杂度）。
2. **连击倍率**：仅做**视觉展示**（如 ×N 徽标/飘字）；**星星/得分资产不动**，score 口径仍 = 答对数 × 10（服务端推导不变）。
3. **词义消消乐难度**：映射 **学段 + 题型分类**（不另建 初/中/高 三档）。
4. **对局暂停按钮**：对局提供暂停；**暂停时遮罩盖住/隐藏关卡画面**（防止偷看计时与题目）；极速模式暂停时倒计时须停表；提供「继续 / 返回」。
5. **新玩法**（含消消乐、连连看等）→ **统一放后面再规划**；当前批次不新增玩法。

## 十、优化项（对齐后纳入需求）

### O1 闯关界面按分辨率自适应（消除“需下拉滚动”）
- 目标：矮屏手机游戏页一屏放下，不需要滚动。
- 现状：Canvas 固定高（900rpx）+ HUD/模式行/底部面板在部分机型超高，出现下拉滚动。
- 方案：
  - 游戏页容器高度 = 视口（不滚动，恢复 `disableScroll`）；
  - Canvas 不再固定高，占「视口 - HUD - 模式行 - 底部面板」的剩余高度（flex）；
  - 渲染按 `scale = min(实际宽/390, 实际高/500)` **等比缩放并居中**（不变形、不裁切；画布背景与页面同色延伸）；
  - 涉及：`pages/game/game.wxss`（布局）、`pages/game/game.js`（onReady 尺寸计算 + 缩放/居中偏移）。
- 验收：375×667 与更矮屏（如 320×568）试玩均一屏、按钮完整、画面不变形。

### O2 注册/登录流程规范化（参照成熟案例）
- 现状问题：onLaunch 即静默登录建档（“游客”实际已注册）；协议在首页以 modal 摘要弹一次；注册动作自动发生，与预期流程不符。
- 目标流程（成熟做法）：
  1. 进入 = **游客模式**：不建档、纯本地，可玩默认前 3 关；数据本地存储；
  2. 点「微信登录 / 注册」→ 先展示 **用户协议 + 隐私政策**，**同意后**才调用微信接口；
  3. 调 `wx.login` → 后端 `/api/login` **建档（注册成功）** → 返回 token；
  4. `needProfile=true` 引导完善昵称/头像 → 解锁完整功能；
  5. 拒绝协议 → 保持游客；游客本地成绩可提示“登录后同步”（合并可选后续）。
- 改造面：`utils/auth`（登录拆为显式注册入口；不再 onLaunch 自动静默建档）、`app.js`、首页登录入口与协议前置、游客数据本地化与受限规则保持一致。
- 实施方式：先出**详细改造设计**（时序/异常/数据迁移）→ 确认后执行。

## 十二、合集扩展架构评估（2026-09-09）

结论：**当前架构可支撑“6 合 1 + 持续扩展”，但扩展前需做一次公共层抽取。**

### 已通用（新玩法可直接复用）
- 词库/题库：本地内置、按学段+题型分类过滤出题（utils/dict + data/*）；
- 用户/成绩/错题/排行/成就/段位：数据模型通用（新增玩法时成绩记录加 `game_type` 即可区分）；
- 网络层 callContainer、登录态/游客规则、声音开关、皮肤渲染。

### 需要扩展前改造（避免每个玩法重复造轮子）
1. **公共对局外壳**：把 HUD（❤/得分/连击/暂停/计时）、结算（星/错题/操作）、错题上报、成绩上报、音效开关、暂停遮罩，从“射击玩法（pages/game + game/engine-renderer）”中抽为可复用外壳/公共模块；
2. **大厅玩法化**：首页由“功能入口”演进为“玩法大厅（2 列玩法卡 + 专区）”；新玩法注册进 `app.json` + 大厅配置即可上入口；
3. **玩法扩展契约**：新玩法 = ①出题来源（复用 dict/词库或独立题库）②对局循环（正确/错误/生命判定）③结果回传外壳（score/错题/连击/星）——套用外壳即获得统一 HUD/结算/上报/合规；
4. 三形态（经典/Boss/极速）属射击玩法内部表现，不影响其他玩法。

### 暂缓项
- 云端题库（保留本地离线）；对象存储素材上传（表情/图标先 emoji 占位）。

## 十四、签到与每日一题（需求，待实现）

> 依据：用户确认「主页去掉全部玩法/错题本/签到/报告/形象/成就/分享/设置；签到与每日一题冲突，**保留每日一题**，每日一题做完即视为今日签到；不做独立签到入口」。

### 结论
- **独立「签到」入口不设**；主页不再出现「签到」Tab/按钮。
- **每日一题 = 签到**：完成当日每日一题，即自动完成「今日签到」，无需额外打卡动作。

### 每日一题规则
- 每天 1 题（可复用词库，按学段+题型分类随机出题）。
- 完成即记「今日已签」；当日重复完成不重复计数/奖励。

### 连续签到里程碑奖励（每日一题连续完成天数）
| 连续天数 | 奖励 |
|---|---|
| 7 天 | ⭐ 星星 |
| 15 天 | ⭐ 星星 |
| 30 天 | 🐲 限定皮肤（示例：龙） |
| 60 天 | 🦄 限定皮肤（示例：独角兽） |
| 100 天 | 👑 徽章/皇冠 |

- 连续中断（隔日未完成每日一题）→ 里程碑天数归零或回退，具体策略待定。

### 待确认

## 十五、自定义题库（UGC 关卡，用户可上传）（需求，待实现）

> 依据：用户提出「学习增加自定义题库 —— 内置模板，支持用户自定义上传题库，要求必须 **10 个一组**；用户自己使用，也可提交审核，审核通过作为新关卡**全网可见**」。

### 目标
- 让用户**自建词库**：用内置模板填词，**10 个一组**成组上传。
- 上传后**本人可立即使用**（个人题库/自建关卡）。
- 支持**提交审核**：通过后作为**新的公开关卡**，全网所有用户可见可玩。

### 内置模板（用户填写的字段）
平台提供统一模板（表格/表单），每条题目字段建议含：
- **题干/词**：单词或成语（word/idiom）；
- **释义**：中文释义（explain）；
- **题型分类**：词义 / 填空 / 词语 / 成语 / 歇后语 等（复用现有 TYPE_GROUPS）；
- **学段/难度**：小学 1-6 / 初中 等（复用现有学段映射）。
- 附加（可选）：例句、图片/音频位（先可不做，占位）。

### 成组规则
- **必须 10 个一组**（一组成一关），不足或超过 10 条不予上传；
- 组内**同题型 / 同学段**为宜（保持一关难度一致），允许用户选择；
- 一关 10 题，计分沿用现有「每题 10 分、满分 100」口径。

### 使用与审核流程
1. **创建**：选模板 → 填 10 条 → 校验（字段完整、无重复、10 条齐）→ 上传入库；
2. **本人使用**：上传后即为「个人自建关卡」，可立即在玩法中游玩（与系统关同流程：HUD/结算/错题上报/成绩上报一致）；
3. **提交审核**（可选）：标记「申请公开」→ 后台审核（内容合规、无敏感词、质量/难度合理）；
4. **通过** → 转为**公开关卡**，进关卡地图，**全网可见可玩**；**不通过** → 反馈原因，用户可修改后重提；
5. **下架/举报**：公开关卡支持举报，违规可下架（待定）。

### 数据与后端
- 需新增 `custom_word`（用户自建词条，含 `owner_openid`、`group_id`、`status`：draft/private/pending/published/rejected）与 `custom_group`（十个一组、成组状态、所有者、审核状态）等表/字段（或复用现有关卡/词表结构 + `source` 字段区分「系统/用户/公开」）。
- 词库原则：现有关键约定是**本地离线词库**（`data/*.js`），UGC 上传需走**云端存储**（云托管 MySQL）——这是与"本地离线"的差异点，需在评审时明确是否破坏离线原则；建议：系统词库保持离线，UGC 词库走云端，仅登录用户可手动作业。

### 待用户确认 / 拍板
1. 审核要不要**全人工**，还是先「机器初审（敏感词）+ 人工抽审」？
2. 公开关卡是否纳入**排行榜 / 成就 / 段位**（还是仅作为一种玩法关卡，独立计分）？
3. 是否限制**每用户上传数量 / 每日上传上限**、审核周期？
4. 自建关卡**是否参与「每日一题 / 错题本」**等（建议参与错题本）。
5. 内置模板**字段是否含图片/音频/例句**（第一期建议先只做文字字段）。

## 十六、闯关模式总规范 + 数独关卡设计（需求）

> 依据：用户提出「**每个游戏都是闯关模式**；具体展示需再规划。例：数独起步 4×4 简单 → 关卡难度持续递增 → 到 9×9，且**给定数字越给越少**。找网上成熟案例，**关卡固定即可**」。

### 一、闯关模式总规范（所有玩法统一）
- **每个玩法 = 一条闯关进度线**，多玩法各自独立关卡线（互不干扰）。
- 关卡表现沿用现有**关卡地图（蛇形路径）+ 星数（1-3 星）+ 解锁顺序**，与现有 word_warrior 关卡逻辑一致。
- 每关结束走统一结算/错题上报/成绩上报（复用公共对局外壳）。
- **关卡固定**：关卡序列与题量预置，不随机重排（保证可复玩、可比对）；用户反复挑战只是刷分/刷星。
- 关卡从 **1 关起连续编号**，按难度**线性递增**（1 最简单，越往后越难），难度升到一定后不再上升（封顶），后续关卡为「挑战重复」或「高难复现」。

### 二、数独关卡设计（示例/曲线）
参照成熟方案：**《全民数独》以「5 大关 × 220 小关」线性递增、覆盖入门到竞赛级，且支持四宫/六宫/九宫**；**《数独》按 四宫/六宫/九宫 三档尺寸分级**；**sudoku.coach 指出难度主要由所需技巧判定，提示数越少通常越难**。

#### 1) 关卡进阶主线（网格尺寸 + 给定数字数）
| 阶段 | 网格 | 给定数字数 | 难度 | 说明 |
|---|---|---|---|---|
| 入门 | 4×4（16 格） | 8~10 | ⭐ | 教学/上手，仅需排除法 |
| 初级 | 6×6（36 格） | 14~18 | ⭐⭐ | 引入行列/宫排除 |
| 中级 | 9×9（81 格） | 34~40 | ⭐⭐⭐ | 常规数独，需简单技巧 |
| 高级 | 9×9 | 28~33 | ⭐⭐⭐⭐ | 需区块/数对等技巧 |
| 大师 | 9×9 | 24~27 | ⭐⭐⭐⭐⭐ | 需链/高级技巧，接近极限 |

- **给定数字越给越少** ⇒ 难度越高（简单 8-10 个 → 大师 24-27 个）。
- 数值为**目标区间/参考值**；具体以「可唯一解 + 所需候选技巧」校验为准（避免仅靠数量定难度）。
- 一关一个**固定题目**（关卡固定），题目预置入库。

#### 2) 关卡编号与星数
- 示例编号：`数独 1-10`（入门 4×4）→ `11-30`（初级 6×6）→ `31-60`（中级 9×9）→ `61-90`（高级）→ `91-120`（大师）……具体档位/关卡数后续定。
- 每关 1-3 星（按完成度/时间/提示使用，三形态之一或仅经典）。

#### 3) 辅助/体验
- **提示（Hints）**：可给出候选数或下一步思路（参考 sudoku.coach/数独玩家「提示解题思路而非仅答案」）；用提示会降星。
- **笔记/候选数标记**：进阶关卡开放（可选）。
- **难度切换**：可不做（闯关已天然分级），或提供「跳过」/「直接选档」。

### 三、玩法分类：两类关卡来源（用户已拍板）
> 依据（用户）：「**除了数独、24点、2048 这三关（数学逻辑类）在网上找成熟案例、固定关卡内容，其他玩法都要结合题库去布置关卡**」。

- **A 数学逻辑类（数独 / 24点 / 2048）**：**关卡内容固定预置**，参考网上成熟案例设计；关卡即题目，可复玩/可比对。
- **B 字词类（字母射击 / 词义消消乐 / 词语连连看 / 单词弹弹球 / 单词贪吃蛇 等）**：**结合题库布置关卡**——关卡内容由词库按「学段 + 题型」出题生成，不固定单题，沿用现有题库机制；关卡难度 = 学段 / 分类（已拍板）。

#### A 类：固定关卡（数学逻辑，线上案例）
| 玩法 | 成熟案例 | 关卡内容固定方式 |
|---|---|---|
| 2048 | 经典 2048（[策略攻略](https://www.youtube.com/watch?v=a9BwvFfE3QI)） | 每关=目标数字（16→…→2048→4096+），逐步提高目标/减少格子 |
| 算 24 点 | 《算24点》[App Store](https://apps.apple.com/tw/app/%E7%AE%9724%E9%BB%9E-%E6%92%B2%E5%85%8B%E7%89%8C%E5%BF%83%E7%AE%97%E5%8F%A3%E7%AE%97%E6%95%B0%E5%AD%97%E9%81%8A%E6%88%B2/id1274499822) | 15 级 / 300 关，由易到难，每关数字组合固定 |
| 数独 | 《全民数独》《数独》(见上) | 每关一张固定盘面（4×4→6×6→9×9，提示数递减） |

#### B 类：结合题库布置关卡（字词，非固定单题）
- 关卡由**词库**按 `学段` + `题型分类（TYPE_GROUPS）` 出题，一关一题或多题（复用现有 `data/*` + 出题引擎）；
- **关卡难度 = 学段 / 分类**（已拍板），不另设初/中/高；
- **关卡内容不固定**（同关不同用户/不同次可能不同题），但**关卡编号/进度线固定**，便于进度排名；
- 经典参考（仅作关卡节奏参考）：《开心消消乐》《Royal Match》三消关卡难度递增（[三消关卡设计](https://zhuanlan.zhihu.com/p/604307837)）、《连连看单机》[百度百科](https://baike.baidu.com/item/%E8%BF%9E%E8%BF%9E%E7%9C%8B%E5%8D%95%E6%9C%BA%E6%B8%B8%E6%88%8F/17533719) —— 继承其"难度递进、目标/步数限制"的关卡节奏，但题目来自题库。

> 说明：两类玩法**关卡进度线都固定**（编号/解锁/星），差异仅在「关卡内题目 = 固定题目（A 类）还是题库出题（B 类）」。两者都天然支持按玩法进度排名（见第十七节）。


### 四、待确认
1. 数独各阶段**具体关卡数**（4×4 练几关、6×6 练几关才能进 9×9）。
2. 关卡是**纯经典**，还是也要套**三形态（经典/Boss/极速）**（建议数独先只做经典，Boss 可做「限时/限步」变体，极速暂缓）。
3. 提示/笔记是否**全玩法通用**，还是数独专属。
4. **关卡固定**是否接受「同一关刷分可重复进」——是（用于刷星）。
5. 是否要为闯关加**连续通关奖励 / 失败重试**机制。

> 参考来源（成熟案例）：《全民数独》[5 大关 220 小关、线性递增、四/六/九宫](https://sj.qq.com/topic/200072651)；《数独》[四宫/六宫/九宫三档难度](https://sj.qq.com/topic/200072651)；[sudoku.coach 难度判定：技巧为主、提示数越少通常越难](https://sudoku.coach/zh-cn/learn/sudoku-difficulty)。

## 十七、排行榜（总榜=星星数 + 各玩法闯关进度榜）（需求）

> 依据：用户提出「**排行榜需要展示每个玩法的闯关进度排名**」「**排行榜可以搞个总榜，就是星星数**」——即排行榜 = **总榜（跨玩法累计星星数）** + **按玩法分榜（各玩法各自的闯关进度）**。

### 目标
- 排行榜分两类：
  - **总榜 = 星星数**（跨玩法累计，用户已拍板）：按玩家**总星星数**排名；
  - **按玩法榜 = 该玩法闯关进度**：每玩法独立，按该玩法下的**闯关进度**排名（数独榜 / 2048 榜 / 24 点榜 / 字词闯关榜…）。
- 玩家可切换查看**总榜**与**每个玩法**的榜单。
- 展示信息：排名、头衔/段位、对应指标（总榜=总星星 / 玩法榜=关卡进度+星）、以及本人的名次高亮。

### 榜单维度（每玩法）
| 玩法 | 排行主指标 | 辅助展示 |
|---|---|---|
| 数独 | 已通关最大关卡号（进度） | 星数合计、段位 |
| 2048 | 达成的最大目标数字 | 总星、局数 |
| 算 24 点 | 已通关关卡数 | 正确率/用时 |
| 词义消消乐 | 已通关关卡（学段+题型） | 最高连击、星 |
| 字母射击 | 已通关关卡 | 星、最高连击 |

### 排序规则
- **总榜（星星数）**：按**累计星星降序**（星星多者靠前），相同再比段位/完成时间。
- **按玩法榜（进度优先）**：
  1. **主排序 = 关卡进度**（谁通关到更后面的关卡谁靠前）；
  2. **同进度 次级排序 = 该玩法星数**（进度相同则星多者靠前）；
  3. 仍相同则按 **完成时间先后 / 连续**（可选，避免并列）。
  - 该规则保留"进度优先"，防止刷低关高分占榜（进度 > 刷分）。

### 榜单类型
- **总榜（星星数）**：全部玩家按**累计星星**排名（跨玩法汇总，**已确定做**）。
- **按玩法榜（闯关进度）**：每个玩法独立榜单，按该玩法闯关进度排名（核心，前 N 名 + 我的名次）。
- **好友榜 / 周榜 / 赛季榜**：可选。参考《全民数独》[在线排行 + 24 级称号](https://sj.qq.com/appdetail/cn.flytalk.shudu)；《数独》按 XP 排名、更难给更多 XP、每周排名（[Sudoku 247 排行榜](https://sudoku247online.com/zh/leaderboard)）；腾讯 [GCloud LeaderBoard](https://gcloud.tencent.com/pages/products/leaderboard.html)（可扩展、动态建榜）。

### 段位 / 称号（进度驱动）
- 段位不再单一按总分，而是**按玩法进度**推进。参考《全民数独》**24 级称号**（入门→竞赛级）。
- 例（数独）：按最大通关关卡对应「新手 → 入门 → 进阶 → 高手 → 大师」；每玩法的段位可独立，也可汇总为总的「战士等级」。

### 数据上报扩展（后端）
- 现状 `scores` 表已含 `grade/level/score/combo/stars`；需在**每局通关**时上报：
  - 该玩法的**最大关卡进度**（`max_level`）与星数，按玩法（`game_type`）聚合 → **按玩法榜**；
  - **累计星星**（`total_stars`）跨玩法累加 → **总榜（星星数）**。
- 建议字段/接口：
  - `rank/progress?game=type` → 该玩法榜单（前 N + 我的名次）；
  - `rank/total` → 总榜（按总星星，前 N + 我的名次）；
  - 表建议 `progress`（openid, game_type, max_level, stars, updated_at）+ `users.total_stars`（或汇总 scores 聚合）。
- 参考：排行榜数据量大，可用腾讯云托管 + MySQL 按时/按玩法建榜，符合当前云托管架构。

3. 是否需要**好友榜 / 周榜 / 赛季榜**（首期建议先只做 总榜（星星）+ 按玩法榜）。
